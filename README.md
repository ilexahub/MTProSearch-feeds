# MTProSearch-feeds

Готовые списки MTProto-прокси для [Выручайки](https://github.com/ilexahub/MTProSearch).

Два разных шага в одном Actions (06:19, 14:19, 22:19 МСК):

1. **Сбор** — как раньше. Скачать открытые источники, формальные проверки, отдать `proxy-ru.txt` / `proxy-en.txt`. К этим адресам раннер **не подключается**. Их живость смотрит телефон.
2. **Пропавшие** — база всех когда-либо виденных `host|port`. Что исчезло из текущего сбора, попадает в отдельный [feeds/check.txt](feeds/check.txt). Только этот файл раннер щупает FakeTLS HMAC (не `req_pq`). Ответил — дописать в те же `proxy-ru` / `proxy-en`.

Если закроется целый открытый источник, адреса из него не пропадают бесследно: они остаются в базе и в `check.txt` по расписанию. С раннера GitHub узел может быть «жив», а у пользователя нет — это не гарантия, только чтобы список не худел в ноль.

## Файлы

| Файл | Что внутри | Приложение качает |
|------|------------|-------------------|
| [feeds/proxy-ru.txt](feeds/proxy-ru.txt) | открытый сбор + ожившие из `check.txt` | да |
| [feeds/proxy-en.txt](feeds/proxy-en.txt) | то же, остальные SNI | да |
| [feeds/check.txt](feeds/check.txt) | пропавшие, очередь HMAC на этот прогон | нет |
| [feeds/archive.json](feeds/archive.json) | все виденные `host\|port` | нет |
| [feeds/meta.json](feeds/meta.json) | время сборки и счётчики | нет |

Источники сливаются в один пул: три корневых файла kort0881, `verified/proxy_us_verified.txt`, `verified/proxy_asia_verified.txt` и 32 сырых URL. География корта файл не выбирает — режет SNI.

## Очередь `check.txt`

Срок — от последнего следа: снова увидели в источниках или HMAC с раннера прошёл. Успешный HMAC сбрасывает срок.

| С момента последнего следа | `check.txt` |
| --- | --- |
| до 30 дней | каждый из трёх суточных прогонов |
| 30–60 дней | нет (только база) |
| окно 2 суток около 60-го дня | да |
| окно 2 суток около 90-го дня | да |
| после этого окна | запись из базы удаляется |

Три прогона в сутки ловят узел, который отвечает только часть дня. Окно двое суток — чтобы один упавший Actions не пропустил дальнюю проверку. Хосты, которые всё ещё в открытом сборе, в `check.txt` не попадают и HMAC не получают.

Проверка пропавших — **одно соединение**, пауза 2–4 с между хостами, не дольше ~50 минут за прогон. Сотни адресов спокойно растягиваются; остаток ждёт следующий из трёх суточных запусков. Так это не выглядит как массовый скан.

## Формальные проверки (шаг сбора, без обращения к прокси)

- валидная ссылка и FakeTLS-секрет с SNI
- порт **443**, **8443** или **853** (DNS-over-TLS)
- SNI не в чёрном списке
- уникальность по `host\|port` (первая подходящая строка)
- корзина: маркер `RU_WHITELIST` → RU, иначе EN (`beboo.ru` в RU)

Белая международная маска в сборщике **не** отсекает EN. Серое в EN режет приложение галкой **TrueMask**.

## Статистика скачиваний

raw.githubusercontent.com / jsDelivr **не** отдают владельцу пофайловые access-логи. Счётчики «из Выручайки» считает отдельный beacon-сервис в репо исходников (`scripts/feeds-stats`, деплой Railway): приложение после успешного fetch шлёт `POST /api/feed-hit`. Прямые открытия этих URL в браузере туда не попадают.

Агрегаты: `GET /api/stats?token=…` → hits / uniques / by_feed / by_channel за ~360 дней. Полная спека и чеклист Railway — в Src: `docs/FEEDS_STATS.md`.

## Сжатие

Канон — `.txt`. На диске gzip ≈ **4×** компактнее; по HTTP CDN часто уже жмёт сам (`Content-Encoding: gzip`). Не публиковать `.zip` как единственный URL (ломает старые клиенты). Опциональный `.txt.gz` — только после поддержки в приложении.
